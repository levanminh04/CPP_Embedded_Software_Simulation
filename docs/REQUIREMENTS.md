# Smart Traffic Light Controller Simulator - Requirements

## 1. Authority and scope

This document is the business-level source of truth for the project.

1. `Mock_Project_CPP_Embedded_Software_Simulation.docx.pdf` is the lecturer's primary specification. Its mandatory requirements and technical constraints take precedence.
2. `Quy định và kịch bản vận hành Smart Traffic Light Controller.pdf` records the team's selected operating rules and advanced scope. It must not conflict with the lecturer's specification.
3. The observable behavior below is fixed. The C++ representation is intentionally open: the controller may use separate enum values, a phase plus direction, and pending flags, or another clear design that preserves these rules.

The program is a C++ console simulation. It models one intersection with two conflicting vehicle directions: North/South (NS) and East/West (EW). A single controller decides the complete intersection state; NS and EW are not independent traffic-light loops.

Out of scope: physical hardware, microcontrollers, GUI, database, network, Web API, camera, AI/ML, lane-level simulation, turning arrows, and real sensors.

## 2. Required system flow

The implementation must follow the lecturer's embedded-software simulation flow:

`simulated sensor/event -> controller -> simulated actuator/output -> display and logger`

`main()` initializes the modules and runs the control loop. Business decisions must not be duplicated in input, output, display, or `main()`.

## 3. Inputs

| ID | Input | Required behavior |
|---|---|---|
| IN-01 | Timer tick | Drives the countdown and time-based transitions. |
| IN-02 | `P` pedestrian request | Latches one pending pedestrian request. Repeated `P` while pending is coalesced, not queued. |
| IN-03 | `E` emergency event | Has the highest operational priority and requests transition to the defined safe emergency condition. |
| IN-04 | Clear-emergency event | Team-defined console/scenario event used to leave emergency mode. The final command spelling is a UI decision. |
| IN-05 | NS/EW vehicle counts | Simulated sensor values used only to select the next GREEN duration for that direction. |
| IN-06 | Configuration | Key/value settings for durations and density thresholds, loaded and validated before normal operation. |

Inputs may be generated by a scenario or entered from the keyboard. All input is validated before the controller acts on it.

## 4. Outputs and visible status

At each control cycle, the console must display:

- NS vehicle light and EW vehicle light.
- Pedestrian light.
- Current controller phase/state name.
- Remaining time when the current phase is timed.
- Pending pedestrian-request status.

The system writes `logs/system.log` using `fstream`. At minimum it logs state transitions, pedestrian requests, and emergency events. The selected team scope also logs pedestrian service, density changes/samples, sensor errors, configuration errors, and invalid input.

## 5. Mandatory business behavior

### REQ-01 - Vehicle signal cycle

Each vehicle direction supports RED, GREEN, and YELLOW. Normal operation alternates the right of way between NS and EW. A vehicle GREEN phase has a finite duration and always changes to that direction's YELLOW before another conflicting direction receives GREEN.

### REQ-02 - Safety clearance

Before granting GREEN to a conflicting movement, the controller provides an ALL-RED clearance interval. In ALL-RED, NS, EW, and pedestrian lights are RED.

### REQ-03 - Countdown and timing

Every timed phase has a visible countdown. Timing uses `std::chrono` and `std::this_thread::sleep_for()` in the application/control loop. The controller receives elapsed/tick information; it does not block on keyboard input.

### REQ-04 - Pedestrian request and safe service

`P` does not turn the pedestrian light GREEN immediately. The request is served at the next safe decision point after the active vehicle phase completes its GREEN, YELLOW, and clearance sequence.

Pedestrian service is exclusive:

- During pedestrian WALK and pedestrian WARNING, NS and EW are both RED.
- The pending request is cleared when service starts, not when it finishes.
- A new `P` during a pedestrian phase creates one request for a later pedestrian phase.
- A pedestrian phase cannot repeatedly take turns without first allowing the next vehicle direction one GREEN phase.

### REQ-05 - Density-based GREEN duration

The selected advanced behavior supports separate NS and EW traffic-density sensor values. Density changes only the finite GREEN duration for the direction about to start; it does not change the NS/EW alternation, bypass safety clearance, override a pedestrian request, or override emergency handling.

The controller samples a direction's sensor before that direction's GREEN begins. A new value during GREEN applies on that direction's next turn.

Default team values are configurable, not hard-coded across modules:

| Setting | Default |
|---|---:|
| GREEN_LOW | 15 s |
| GREEN_MEDIUM | 20 s |
| GREEN_HIGH | 25 s |
| YELLOW_TIME | 3 s |
| ALL_RED_TIME | 2 s |
| PED_WALK_TIME | 10 s |
| PED_WARNING_TIME | 5 s |
| LOW threshold | 0-5 vehicles |
| MEDIUM threshold | 6-15 vehicles |
| HIGH threshold | 16+ vehicles |

### REQ-06 - Emergency mode

Emergency has priority above pedestrian service, normal cycling, and density optimization. The safe emergency condition is:

`NS = RED, EW = RED, Pedestrian = RED`.

The controller must preserve clearance safety rather than changing a vehicle GREEN directly to RED. In business terms, an emergency occurring during vehicle GREEN completes the required YELLOW and ALL-RED path before entering emergency; an emergency during pedestrian WALK allows pedestrian warning/clearance before emergency. If already in a clearance phase, the controller finishes the relevant clearance and then enters emergency.

After the clear-emergency event, the controller does not resume an old countdown. It starts a new deterministic normal cycle from a safe ALL-RED startup path and then grants NS the first GREEN turn. A pending pedestrian request remains pending until it can be served safely.

### REQ-07 - Validation and abnormal handling

The project must handle at least two abnormal cases without crashing:

1. A negative or otherwise invalid sensor count is not classified as normal density. It is logged as `SENSOR_ERROR`; the active timer is unchanged and a safe fallback duration is used when that direction next starts GREEN.
2. Invalid configuration, such as non-positive durations or invalid threshold ordering, is rejected. The system logs `CONFIG_ERROR` and uses the full default configuration.

Invalid keyboard/scenario commands are reported and logged as input errors; they must not corrupt the controller state.

## 6. Invariants and priority

The controller must enforce these invariants at all times:

1. NS GREEN and EW GREEN never occur together.
2. Pedestrian GREEN never occurs with a vehicle GREEN.
3. Pedestrian WALK or WARNING requires NS RED and EW RED.
4. Emergency requires all lights RED.
5. Vehicle GREEN is finite and is followed by that direction's YELLOW.
6. A request accepted for pedestrian service is not silently discarded.
7. Density never changes the direction alternation or a GREEN duration already in progress.

Decision priority is: safety, emergency, clearance/transition completion, pedestrian request, normal vehicle alternation, then density-based duration selection.

## 7. Acceptance scenarios

| ID | Scenario | Expected result |
|---|---|---|
| AT-01 | Normal operation | Vehicle movement alternates with GREEN -> YELLOW -> ALL-RED; countdown and logs are visible. |
| AT-02 | `P` during vehicle GREEN | Request is logged and served only at the next safe decision point. |
| AT-03 | Pedestrian WALK | Pedestrian is GREEN while both vehicle directions are RED. |
| AT-04 | Repeated `P` | Multiple presses while pending produce one pending service, not a queue. |
| AT-05 | `P` during pedestrian phase | The new request waits until at least the next vehicle GREEN phase completes. |
| AT-06 | Emergency during vehicle GREEN | The system follows clearance, enters all-RED emergency, and logs the event. |
| AT-07 | Clear emergency | The old countdown is discarded; the normal cycle safely restarts from NS. |
| AT-08 | Density change | The next relevant GREEN duration changes, but NS/EW order does not. |
| AT-09 | Invalid sensor input | Error is logged; no invalid density decision or crash occurs. |
| AT-10 | Invalid configuration | Default configuration is used and the error is logged. |

## 8. Technical and delivery constraints

- C++ console application; no external library is required.
- Split public declarations in `.h` files from implementations in `.cpp` files when a module has a public contract.
- Use meaningful class/function names, `enum class` where suitable, and basic `array`/`vector` when needed.
- Keep durations and thresholds in configuration/constants, not scattered magic numbers.
- Provide build/run instructions, test cases with results, diagrams, logs, and meaningful commits from every member.
- The team must be able to explain the controller's next-state and output decision in the defense.

## 9. Design freedom kept open

The following are intentionally not fixed by this requirements document:

- Exact `enum class` member names and the number of internal states.
- Whether ALL-RED destinations are represented as distinct states or as one phase with direction/pending metadata.
- Class names and file granularity, provided module responsibilities remain clear.
- Exact keyboard command syntax and scenario-file format.
- The internal parser implementation for `default.cfg`.

Any implementation choice must preserve the requirements, invariants, diagrams, and acceptance scenarios above.
